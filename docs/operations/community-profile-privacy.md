# Community profile privacy (COMM-02 implementation note)

Profiles are separate from member credentials and contact records. Anonymous Payload REST and GraphQL reads of `profiles` and `relationships` are denied; public reads use a fixed version-1 projection. The projection checks account state, profile visibility, per-field audience, site-scoped bidirectional blocks, and governed media before returning data. Responses are private/no-store. Directory results contain only this projection, never email, wallet, credential, audit, or relationship records. A follow does not create marketing consent.

Privacy site scope is derived from `site-settings.canonicalOriginsBySite` and the request host. A deployment with one active site may omit that map; a deployment with multiple active sites must configure unique host ownership or member profile/directory/relationship reads fail closed. Caller-provided `siteId` must match the resolved host site. This prevents a request from switching to another site's block graph.

Members edit display name, handle, bio, visibility, discovery opt-out, field audiences, safe HTTPS links, locale/time zone, and image descriptions from member settings or the authenticated profile API. Handle changes use the COMM-01 canonicalization and cooldown; old handles redirect to the current public URL. Suspended, deleted, private, and blocked profiles return unavailable to unauthorized viewers. Unlisted and opted-out profiles have `noindex` metadata and are excluded from directory queries. Public image URLs appear only if the media governance service approves delivery.

`POST` and `DELETE /api/community/relationships` create/archive site-scoped follow, block, or mute edges. Writes require member session and CSRF. Blocks prevent profile reads and new follows, and the existing discussion/conversation/message/notification policy checks recognize site-scoped block keys. The legacy block endpoint delegates to the same write policy. Owner export includes outgoing relationship records; final deletion archives edges and removes profile fields while retaining required security/moderation evidence.

Block is bidirectional for member profile access, new conversations, message delivery, and existing member-authored discussion reads; anonymous access to otherwise-public content is unchanged. Mute is asymmetric: only the muting member hides the other's discussion posts and notifications. It does not prevent the muted member from reading public content or sending a permitted message. New recipient realtime wakeups are suppressed for blocked/muted pairs, and existing notifications are filtered when read. Moderation reasons remain in audit data, not site-wide realtime payloads.

## Output-boundary audit update — 2026-09-21

Implemented Community boundaries now re-evaluate the same server-side policy on profile and directory projections, discussion/comment reads, notifications, recipient realtime events, and conversation/message reads. Conversation retrieval is site-scoped and participant-checked; a later block makes the conversation unavailable, while a later mute removes only the muting member's incoming messages. Sender account state is rechecked for every message read, so suspended or deleted senders cannot leak through a previously cached conversation response. Message reads are `private, no-store`; profile and directory responses remain `private, no-store`. Member-originated comments, threads, replies, reactions, conversation creation, and messages use the shared process-local 30/minute server throttle. This is a fallback layer; production still needs an equivalent distributed/edge limiter.

The focused threat-model unit probes cover reader/author/third-member cache replay, a post-interaction mute, sender suspension, profile mute asymmetry, old notification filtering, recipient realtime suppression, role-denied moderation, and write-rate exhaustion. They also retain raw-profile projection checks so credentials/contact fields cannot serialize. These are code-level probes, not browser or PostgreSQL release evidence.

Unsupported or not-yet-implemented surfaces are explicitly not claimed: there is no Community-specific GraphQL resolver, member directory/search index, member feed, mention parser, cache invalidation worker, or public community SSE endpoint to audit. Payload REST/GraphQL raw profile access is staff-only; editorial feeds/search/SEO do not currently consume Community profile data. The existing `/api/realtime/stream` serves authenticated team-collaboration scopes, not Community members, so it is outside the Community delivery contract. Any future boundary that emits a member-derived name, handle, image, authored item, or relationship state must call the projection/policy service at emission and at cached replay.
