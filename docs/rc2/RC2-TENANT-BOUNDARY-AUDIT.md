# Tenant Isolation & Module Boundary Audit (special pass, Nov 11 2026)

Commissioned by Matthew (Nov 11, 2026) as a deep audit beyond RC2-A-03's
sampling: enforce tenant isolation throughout the data layer and clean
boundaries between independent modules. Read-only audit; no code changed.
Inspected tree: main `d438b3b03e1637aa9d309359046e2da22fa93281`.

**Publication note:** this document names two unfixed P0 vulnerabilities
with their exploitation paths. It is held from the public repository
until the P0 fixes land; the fix PRs and this audit are then published
together, consistent with the project's transparency standard.

## Executive summary

- **P0 security issues: 2** — both cross-tenant writes reachable with
  ordinary (or no) credentials. Detailed as TA-P0-1 and TA-P0-2 below.
- **P1: 5** (2 security, 3 architecture). **P2: 6.** Full register below.
- **The architecture underneath is fundamentally sound.** Tenant
  derivation was enumerated across 17 mechanisms: 13 SAFE, 1 PUBLIC-ONLY,
  3 SUSPECT (the two P1 security items and TA-P0-1 live there). The
  privileged-access census (1,803 `overrideAccess: true` sites, 242
  files) found exactly **one** confirmed instance of the dangerous shape
  (caller-id write with no independent check) — TA-P0-2 — across every
  id-addressed handler family read end to end.
- **Data layer: no demonstrated cross-tenant private read or write** on
  any of the 8 surfaces audited (SQL, storage, search, analytics,
  exports, webhooks, public routes). Redis and Neo4j are verifiably
  absent; PostgreSQL is the only store.
- **Boundaries:** 5 real import cycles (computed over 938 files / 2,047
  edges), including a 17-file knot and a foundation layer that imports
  upward. Interfaces exist by convention and are largely respected, but
  the convention is undocumented and unenforced.

## Violations register

### P0 — security (fix first, one bounded issue at a time)

**TA-P0-1 — Social account `connect` overwrites another tenant's
account, including its credentials.** POST
`src/app/(frontend)/api/admin/social/accounts/route.ts`: the grant check
runs against the caller-supplied `body.siteId`, but when `body.accountId`
names an existing account the record is loaded by id
(`overrideAccess: true`, ~L343–351) and updated (~L365–382) with
caller-controlled `displayName`, `capabilityState`, `credentialHealth`,
and a `connectionReference` built by encrypting caller-supplied
credentials — with no comparison of the record's own site against the
grant. An operator authorized for one site can silently replace another
site's social account credentials (hijack or sever its publishing
identity). The sibling `test`/`disconnect` actions in the same file DO
check `existing.site` (~L113–123, ~L163–173): the omission is local to
`connect`.

**TA-P0-2 — Unauthenticated crypto settlement with replayable evidence
and no tenant binding.** POST
`src/app/(frontend)/api/commerce/crypto/verify/route.ts` takes
`{intentId, transactionId}` with no auth, no session, no CSRF check, and
no host→site comparison (every sibling commerce route has one). On
acceptance it privileged-updates the intent to `paid`, the checkout
session to `completed`, and settles the order via `finalizeVerifiedOrder`
(`src/modules/commerce/service.ts:601`). The only chain adapter is the
fixture adapter: verification is a lookup into `fixtureObservations` on
the merchant connection (`service.ts:435,466`; matching rules
`contracts.ts:351`). Destination (the merchant's own wallet) is identical
on every invoice and amounts repeat with catalog prices, while
transaction-id dedupe is scoped to a single invoice — so one observed
transaction settles unlimited later same-price intents, for any tenant,
from any host, without sending funds. Precondition, stated plainly: the
merchant connection must carry fixture observations — currently the ONLY
configuration in which Simple Crypto Pay can verify anything (no real
chain adapter exists; A-02 #53). With empty observations the route is
inert.

### P1 — security

**TA-P1-1 — Social draft variant updates are not bound to the checked
draft.** POST `src/app/(frontend)/api/admin/social/drafts/route.ts`: the
draft's site is checked, but variant updates apply by caller-supplied
variant id without verifying the variant's parent draft/site, resetting
approval fields; the create path likewise accepts unverified
`accountId`s. Contained at dispatch — the social worker re-validates
`draft.site === account.site` and the approval hash before any provider
call — so it cannot publish under a victim account. Confined to
unpublished draft content.

**TA-P1-2 — Thread subscriptions trust a caller-supplied identity
header.** `src/app/(frontend)/api/v1/sites/[site_id]/threads/[thread_id]/subscriptions/route.ts`
(GET/POST/DELETE; the only route with this pattern): when no session
resolves, identity falls back to the `x-member-id` header (L36, 61, 87),
and `src/modules/community/thread-lifecycle.ts` reads/writes
`comment_thread_subscriptions` by that member id, ignoring the path site.
Unauthenticated impersonation limited to low-sensitivity subscription
state; the referenced `actor.userId` is never set by the resolver — the
fallback looks like leftover scaffolding.

### P1 — architecture

**TA-P1-3 — The 17-file import knot.** Computed over the full tree
(938 files, 2,047 import edges): a 17-file value-import cycle spanning
collaboration, editorial, media, and presentation, hubbed on
`src/modules/media/workflow.ts`, which imports the presentation component
registry (`presentation/registry.tsx`) while the registry imports media
workflow and editorial persistence back. A backend service importing a
`.tsx` component registry that imports it back is the sharpest
dependency inversion in the tree.

**TA-P1-4 — The foundation layer imports upward.**
`src/modules/core/site-settings.ts` imports `presentation/request-theme.ts`,
`presentation/registry.tsx`, and `public/semantic-url.ts`;
`public/site-scope.ts` imports core back, closing a 3-file cycle. `core`
is the most-depended-on layer and sits _above_ two higher layers in the
real graph.

**TA-P1-5 — Editorial ↔ public share hierarchy/URL logic in both
directions** (4-file cycle: `editorial/hierarchy.ts`,
`public/hierarchy.ts`, `public/discovery.ts`,
`public/semantic-url-service.ts`) with no owning side — the concrete
loop behind RC2-DEBT-12's layering observation.

### P2

- **TA-P2-1 — Moderation action writes carry no tenant predicate.**
  `src/modules/community/moderation-actions.ts` runs UPDATEs keyed by bare
  target `id` (L205–458). Safe today only because the enclosing case is
  loaded site-scoped upstream; the write layer itself is unguarded.
  Defense-in-depth.
- **TA-P2-2 — Transactional cross-module data reads without an
  interface.** `src/modules/audience/service.ts:917–931` reads the
  `spaces` collection directly (privileged) for segmentation facts;
  `src/modules/analytics/operator-report.ts` reads commerce `orders`
  directly (also the root of A-03 seam #7's friction). Platform reads
  (search projection, portability's ~30-collection sweep, onboarding) are
  the same pattern by design and are named as a class to govern, not
  violations.
- **TA-P2-3 — Interface convention is undocumented and unenforced.** No
  per-module barrels, no boundary lint; the de-facto entry files
  (`service.ts`, `site-scope.ts`, `operator-grants.ts`, …) are largely
  respected (true internal reaches are few and named in the evidence), so
  this is governance debt: it will drift without a guard.
- **TA-P2-4 — Two intra-module cycles** (community notifications cluster,
  5 files; conversation-composer ↔ message-attachments, 2 files).
  Internal tangles, not boundary violations; they make the community
  service file a hub in unrelated findings.
- **TA-P2-5 — `assertExecutionScope` has no production caller.** Job
  handlers trust the persisted execution-event row (server-created only).
  Sound today; recorded as a defense-in-depth note.
- **TA-P2-6 — Switcher-cookie and grant patterns are per-route
  discipline, not a shared enforcement point.** Every consumer found
  re-authorizes correctly, but a future route can forget; there is no
  single choke point to inherit from. (Same family as TA-P2-3.)

## Existing safeguards (verified in code, credited)

- Fail-closed host resolution (`publicSiteForHost`): ambiguous or unknown
  hosts resolve to no site, never to a default tenant.
- Per-site community authority (`resolveCommunityActor`): identity first,
  then per-site role rows; a staff identity alone grants nothing.
- The operator-grant system (`operator-grants.ts`): child-record
  authority derives from the persisted parent — "never a caller's site
  hint" — used uniformly across the admin route family and collections.
- Host-bound tenant selection in commerce/public APIs: caller site values
  are rejected on mismatch (analytics collect, checkout status, download
  grants, experiences).
- Check-after-fetch discipline across id-addressed handlers (receipts,
  releases, webhook retry, session revoke, media): object site compared
  to grant/host/session before data returns or mutation lands.
- The cart is never caller-addressed (resolved from host + session/guest
  token hash). Machine API credentials are bound to one site; every
  query derives from `credential.siteId`.
- Job discipline: site comes from persisted records/events, never job
  input; jobs API is owner-only.
- Database-level enforcement for comment threads: FK +
  `UNIQUE(site_id, canonical_content_id)` + a site-match trigger.
- Capability URLs done right: HMAC-derived, hash-stored download grants
  (host-site + member bound, expiring, revocable); signed POD asset URLs;
  192-bit preview tokens, hash-stored, creator-session-bound, access
  re-checked at use.
- Search re-authorizes every hit against the canonical record's site;
  exports are single-site by construction; member export is session-
  bound and rejects a foreign `memberId`.
- The social dispatch worker re-validates draft site, account site, and
  approval hash before any provider call (contains TA-P1-1).
- Adversarial suites exist and pass on the patterns above
  (`tenant-authorization-matrix`, `adversarial-cross-site-matrix`,
  `community-cross-site-boundaries`) — no equivalent negative test covers
  TA-P0-1, TA-P0-2, TA-P1-1, or TA-P1-2.

## Remediation plan (dependency-ordered)

Each step is one bounded issue, behavior preserved except where insecure,
with its negative cross-tenant test executed before the step is called
done. Steps 1–2 are independent of everything else and land first. No
sweeping refactor anywhere in this plan.

**Step 1 — TA-P0-1 (social accounts `connect`).** Before the update, load
the account and require `existing.site ∈ grant.authorizedSiteIds` (global
owners excepted) — the exact check the sibling actions already perform.
_Regression risk: minimal_ (the check exists twice in the same file).
_Tests:_ new negative integration case — single-site operator attempts
connect against a foreign account id → 403/404 and the foreign record is
byte-identical afterward; positive case (own-site connect) unchanged.

**Step 2 — TA-P0-2 (crypto verify).** Three bounded changes in one route:
(a) bind the request to a tenant — require the intent's site to equal the
host-resolved site, as every sibling commerce route does; (b) make
fixture observations single-use across intents (a consumed-observation
record keyed by transaction id per merchant connection, checked and
written in the settlement transaction); (c) state on the record that
fixture evidence is test evidence — settlement via fixture adapter must
be impossible when the app runs in production posture unless a real
chain adapter is configured (the deployment check fails closed, like the
other production-posture guards). _Regression risk: low_ — the feature's
only working configuration is test setups; legitimate same-price repeat
purchases are unaffected because each produces a distinct transaction.
_Tests:_ replay case (same transaction id, second intent → rejected);
cross-tenant case (intent of site B posted to site A's host → 404);
unauthenticated settlement attempt remains impossible after the fix's
auth/host binding.

**Step 3 — TA-P1-1 + TA-P1-2 (social drafts; subscriptions header).**
Bind variant updates to the checked draft (variant.parent === draftId, or
re-derive the variant set from the draft rather than caller ids); verify
`accountId` belongs to the draft's site at create. Remove the
`x-member-id` fallback entirely — no session, no subscription access
(the dead `actor.userId` reference confirms it is scaffolding).
_Regression risk: low_ (both paths are operator/edge surfaces; the UI
uses sessions). _Tests:_ foreign variant id → rejected, draft unchanged;
header-only subscription attempt → 401/404.

**Step 4 — TA-P2-1 (moderation write predicates).** Add `site_id` to the
moderation-actions UPDATE predicates (case's site, already in scope).
_Regression risk: minimal_ — predicates only narrow. _Test:_ existing
moderation suites re-run; a crafted foreign target id is a no-op (can be
an integration case in the A-04 world).

**Step 5 — Boundary governance (TA-P2-3, TA-P2-6; executes RC2-DEBT-12's
measure).** Document the de-facto module entry files as the public
interfaces (a short BOUNDARIES note per module folder or one registry
section), and add an automated import-cycle check to the verify chain,
baselined at the current 5 SCCs so the count can only shrink.
_Regression risk: none to runtime._ _Measure:_ cycle count in the gate
output; new cycles fail CI.

**Step 6 — Break the cycles, smallest first (TA-P1-4 → TA-P1-5 →
TA-P1-3).** (a) Core triangle: move the theme/semantic-url lookups out of
`core/site-settings.ts` behind injected lookups or a leaf module both
sides may import — core must import nothing from presentation/public.
(b) Hierarchy: assign single ownership (public owns hierarchy projection;
editorial consumes it through the public entry file, not vice versa).
(c) The 17-knot: extract the media workflow's dependency on the
presentation registry behind a narrow interface (the workflow needs
component _metadata_, not the registry component map), and untangle the
collaboration↔editorial persistence edge. Each sub-step is its own PR
with the cycle check from Step 5 proving the SCC shrinks and the full
gate chain proving behavior. _Regression risk: medium_ — import cycles
can hide initialization-order assumptions; the full verify chain +
targeted family suites run per sub-step, and no sub-step changes runtime
logic, only import structure.

**Step 7 — Govern the transactional cross-module reads (TA-P2-2).**
Route segmentation's space fact through the identity/community entry
file (or accept it formally as a platform read in the Step-5 note — the
decision is recorded either way); give commerce an analytics event
emission or a named reporting interface so the operator report stops
reaching into `orders` (this also closes A-03 seam #7's friction).
_Owners:_ H-03/H-04 territory; sequenced after the H-03 profile/space
merge design, which changes what the segmentation read even is.
