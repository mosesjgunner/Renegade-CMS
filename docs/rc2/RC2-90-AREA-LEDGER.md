plus its merge commit), Nov 11, 2026. Scope authority: the reconciled

**How to read this:** E-levels follow the ladder literally (E0 concept/stub,
E1 mounted useful action, E2 connected workflow with scoped permissions and
a proven negative case, E3 operationally supported, E4 mature). Levels rest
on code inspection plus previously _executed_ proof (RC1 record, GUI pack
evidence). Sandbox/harness proof is labeled and never counts as live
provider verification. Where evidence could not settle a level the row says
NOT VERIFIED. Provider-dependent rows state the Renegade-side contract
level; the live-provider gap is in Missing proof.

## Cross-cutting findings (for A-03's seam register and the H batches)

1. **Community runs a bespoke SQL shadow domain.** Comments, private
   messaging, moderation reports/cases/actions, reactions, and community
   policies live in raw SQL tables (comm-\* migrations) written directly by
   the service layer, not in Payload collections. It works and is well
   tested, but Payload access control, admin, and portability tooling do
   not see these records — the sharpest "one canonical record per domain"
   question in the codebase. A-03 owns the seam analysis; nobody should
   improvise a migration off this note alone.
2. **Gate-boundary straddles of the NEW-01 shape.** Three surfaces mount on
   the lean floor while parts of their machinery sit behind optional
   modules: the Quality Center's audit surface (floor) vs its collections
   and scan task (`quality`); donation/subscription surfaces (floor) vs the
   payment core (`commerce`); the AI family registered on the floor but
   claimed by no optional module at all, so it cannot be switched off via
   `RENEGADE_MODULES`. No defect is alleged in any of the three — the
   floor behavior is _unproven_, which is exactly the shape NEW-01 had.
   A-03 names them; H-02/A-04 fixture work proves or breaks them.
3. **Gate-label drift between documents.** `docs/rc/CAPABILITY_LEDGER.md`
   labels telecom and automation-runs "floor"; the registry claims them
   under `newsletter`/`notifications`. The registry governed this ledger;
   the drift is an A-03 reconciliation item.
4. **Two webhook systems coexist** (delivery engine in
   `src/modules/integrations/webhooks.ts`; subscription/tool types in
   `src/modules/extensions/api.ts`). They look complementary; A-03
   confirms there is exactly one canonical subscription store.
5. **Adapter-only is the honest norm for anything leaving the box.**
   Social dispatch (12 adapters, local harness), newsletter (local sink),
   telecom (emulator; a real-provider file exists but is disabled),
   payments (Stripe test-mode + local test checkout), POD (loopback
   simulator; a real Printful adapter exists unproven), federation (local
   peer), AI (loopback protocol harness). No live external delivery of any
   kind is verified anywhere in the 90 — by design at this stage, and the
   ledger says so per row instead of letting "E2" imply it.
6. **Types-only scope areas:** #7 (grammar contracts), #22 (offline types),
   #28 (a task-type string), #60 (real agent logic no route reaches).
   Under the ladder, declarations are E0 — plausible-looking code is how
   NEW-02 happened.
7. **Performance is unmeasured** (#88): tooling exists, no baseline,
   budget, or timing data exists anywhere. H-06 creates the first one;
   until then every speed claim about this codebase is unsupported.
8. **Freshness caveat on the E3s:** #79/#82/#83/#89's deepest receipts are
   RC1-candidate-bound. The mechanisms run on current HEAD (the A-01
   baseline chain exercised migrations, upgrades, jobs, and the full gate
   chain), but the full restore/upgrade rehearsals re-run at H-08.
