## Durable contract to implement

All mutable requests must resolve the current principal and tenant server-side. A proposed Creator capability is a site-scoped grant to a member for a named operation; object ownership or an explicitly delegated role must also be checked. Revocation and suspension take effect on the next request. An idempotency record must bind tenant, actor, operation, key and canonical request hash: identical retries return the existing result, and reuse with different content fails. Request-specific authorization is repeated even for a replay. Persist a job/outbox entry in the same transaction as the initiating state where applicable; a worker must reconcile an uncertain external outcome before retrying it.

Proposed transitions, subject to pass-specific implementation and tests:

| Aggregate        | Normal edges                                                                                | Failure and recovery edges                                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capture          | draft → preflight → ready → recording → stopping → processing → completed                   | Any pre-terminal state may become cancelled when safe; recording/stopping may become recoverable when durable chunks exist; failed/recoverable may return to processing only after validating the manifest.                       |
| Live event       | draft → scheduled → lobby → starting → live → ending → ended → replay-processing → archived | Starting/live may become recoverable on connection loss; reconciliation returns to the correct prior live/ending state or records a failure. An output attempt failure does not transition the event or discard source recording. |
| Upload           | staged → inspecting → ready or quarantined → review → approved → published                  | Inspection/review may reject; ready or later may be removed under retention policy. A quarantined item cannot publish and returns to inspection only after a successful rescan.                                                   |
| Delivery attempt | unconfigured → validating → ready → connecting → live → ended                               | Connecting/live may enter reconnecting, then live or failed; revocation blocks retries. A new attempt after terminal failure requires explicit policy and a new attempt identity.                                                 |
| Processing job   | queued → running → succeeded                                                                | Running may become retryable after lease expiry or failure; retryable → queued; queued/running may become cancelled when safe. Terminal success must identify output checksum and source/recipe versions.                         |

Implement guards with compare-and-set or row locks, explicit retry/recovery edges, terminal-state rules and audit events. Transitions require server-side authorization and persisted version checks; no processing completion implies publication approval. These are proposed contracts, not code or evidence that every edge is implementable on every provider. Pause/resume, cancellation races, failure classification and restart reconciliation need executable tests for each pass.

## Migration dependency graph

1. Existing sites, members, member-site roles, profiles, Spaces and media assets precede any creator policy/grant or owned object.
2. Existing content, album/media usage and optional media registrations precede project references; keep publishing lifecycle and source bytes canonical.
3. A capture or edit record requires scoped ownership and immutable asset references; rendering requires existing media task infrastructure and optional heavy workers.
4. A live event requires scoped host/room references; delivery attempts and replay references follow the event and provider configuration. Secrets must not enter public projections or fixtures.
5. Existing Rooms tables come from `20261121_170000_rc315b_groups_rooms`; existing catalog tables come from `20261121_190000_rc312_creator_catalog`. Do not recreate either. Add forward-only additive migrations, foreign keys and indexes after checking clean-install and RC2/RC3 upgrade data. Disabling a module must not delete canonical data.

The actual Creator schema, indexes, route contracts, rollback and downgrade boundaries remain to be designed and tested per pass. No migration has been added by CRE-00.
