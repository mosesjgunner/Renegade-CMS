## 2. What this card changes (design)
Reorganization, **not deletion**. Every collection still lives in the codebase. Only *which*
collections are **registered with Payload on a default install** changes.

- **Root cause fixed:** the app composes ~161 Payload collections. Payload's built-in
  "locked documents" dashboard query builds a single PostgreSQL `json_build_array(...)` with
  ~1 argument per registered collection. PostgreSQL caps a function call at **100 arguments**,
  so ~161 collections make `GET /admin` fail with a cryptic HTTP 500 (SQLSTATE **54023**).
- **Fix:** a default install registers only the lean **CMS floor** (29 collections). Outer-ring
  collections are grouped into **17 optional modules**, OFF by default, switched on with one env
  var. The registered count drops far below 100, so `/admin` renders.

## 4. How the flags work / how a user turns a module on
Two orthogonal env vars, read at server startup:
- `RENEGADE_MODULES` — comma list of module ids to enable. Unset/empty = floor only.
  `"all"` = every module (only for artifact generation). Whitespace-tolerant, case-insensitive;
  unknown ids throw a clear error listing valid ids.
- `RENEGADE_ALLOW_UNSAFE_COLLECTION_COUNT=true` — bypasses the hard PG count guard. Reserved for
  regenerating full-set `payload-types.ts` / import map; **not** for serving.

Example — enable Commerce and Newsletter on a deployment:
```
RENEGADE_MODULES="commerce,newsletter" npm start
```
This registers the 29 floor collections + 10 commerce + 12 newsletter = 51 collections (still
well under the limit). Enabling everything trips the guard on purpose.

**Count guard** (`assertCollectionCountWithinLimit`): throws a loud, explanatory error at
`count >= 100` (before PostgreSQL would 500), and warns at `count >= 90`.

**Relationship pruning:** three floor collections have relationship fields that point at
optional collections (`media-assets.collections → albums`, `content.relationships →
relationships`, `article-family-content.source → sources`). Payload's `buildConfig`
hard-rejects a relationship whose target is not registered (`InvalidFieldRelationship`), so the
gate prunes those fields when the target module is off and restores them when it is on. Gated
DB columns/tables are untouched — the field is simply not surfaced at runtime.
