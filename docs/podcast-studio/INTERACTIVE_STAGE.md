# Interactive Podcast Studio

Open a Podcast Studio session, issue guest links from the lobby, and check the host devices before opening the stage. Guests use the existing single-use link, check their camera and microphone, declare headphones or speaker fallback, and wait backstage. The existing show consent policy still governs admission. A guest can decline camera use in the recording and audience program while staying on the call and sharing a private camera preview with the host.

The host has a mute control for each admitted microphone. Host mute takes that input out of the audio program and every guest return. Releasing host mute leaves the guest's own mute preference in effect. The lobby's Kick guest and Revoke actions apply to the stage as well. The browser opens at most three guest connections. Each return mixes the host and other guests while excluding its recipient's microphone. Browser echo cancellation is on, and headphones are recommended on both ends.

A guest's camera decision is carried by the authenticated answer for that invite, negotiation attempt, and video transceiver. Only a matching camera track ID, matching media ID, and explicit opt-in allow it into the compositor. A guest can withdraw during a call, which stops that camera and signals the host to remove it. Guest microphone audio may reach the program after admission. Guests see the program recording state and a separate camera consent status.

## Program outputs

The host selects solo, side-by-side, grid, or screenshare with picture-in-picture. Browser screen capture shares video from a host-selected source. The program canvas and mixed audio feed a downloadable WebM and the theater video publisher. To publish video, select an existing theater room ID and use that room's broadcast operator account in the same browser. The theater's normal publisher, access rules, and audience player apply. A Podcast Studio operator grant alone does not confer theater publishing rights.

For an audio-only show, the program audio can instead feed the existing Podcast Studio live ingest. It uses the session's configured relay. Start the appropriate broadcast before directing an audience to it. The WebM stays in browser memory until downloaded. The interactive stage uses the mixed program recorder. Separate guest ISO capture and conform remain available at the service layer and are outside the interactive stage's recording controls.

## LiveKit self-hosted evaluation

Keep the browser stage within its three-guest cap. The host makes one WebRTC connection and one mix-minus return per guest, so its encoding and upstream needs grow with the number of guests. MediaMTX fits the current theater infrastructure as the audience relay and was exercised with the shared stage program. LiveKit remains the candidate for larger interactive calls. Its SFU can forward participant tracks and handle adaptive subscriptions. MediaMTX testing here covered receiving and distributing a single mixed program. No alternative group-call SFU benchmark was run. [LiveKit deployment](https://docs.livekit.io/transport/self-hosting/deployment/)

The standalone [interactive-studio Compose file](../../compose.interactive-studio.yaml) declares the server, Egress worker, and private Redis service under the `interactive-studio` profile. Redis is required for the self-hosted Egress message bus and is also used by distributed LiveKit deployments. The core CMS has no dependency on this file. To configure an evaluation host, supply pinned images and paths to operator-managed server and egress configuration files using the `STUDIO_*` variables in the Compose file. Set the server's API port to 7880, ICE/TCP port to 7881, and ICE/UDP mux port to 7882. Configure its reachable ICE address and HTTPS/WSS proxy. Point both services to `studio-redis:6379` and the worker to `ws://studio-livekit:7880`, with the same operator-managed API credentials. Use `/recordings` for worker output or configure object storage. The Compose profile was rendered with fixture settings. The SFU and Egress services were not started in the acceptance run. [LiveKit ports](https://docs.livekit.io/transport/self-hosting/ports-firewall/) · [Egress service](https://docs.livekit.io/transport/self-hosting/egress/) · [Distributed deployment](https://docs.livekit.io/transport/self-hosting/distributed/)

For an SFU integration, keep token minting behind the CMS admission check and scope grants to the invite's room and identity. Use short-lived grants and actively remove revoked participants. Self-hosted LiveKit removal does not invalidate an already issued token. Keep raw backstage tracks out of Egress by using a separate program room with only consent-filtered media, or use a custom composite that subscribes to an authorized program-track allowlist. Room Composite's default view can include participant camera tracks. A consent-aware composite or program room can feed both a file and a live output from the same source. Measure mixed output CPU independently of SFU forwarding capacity. [Tokens and revocation](https://docs.livekit.io/frontends/reference/tokens-grants/) · [Custom templates](https://docs.livekit.io/transport/media/ingress-egress/egress/custom-template/) · [Outputs](https://docs.livekit.io/transport/media/ingress-egress/egress/outputs/)

## Acceptance evidence

| Check                          | Observed                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Guest authorization            | Existing PostgreSQL journey and real signalling handlers exercised admission, concurrent single-use invite redemption, cross-room rejection, and revocation on a migrated disposable database.                                                                                                                                                             |
| Browser media and consent      | Three independent Chromium processes on one workstation with synthetic camera/mic devices and fixture signalling. Both private previews appeared, and the compositor omitted the camera that declined. The guests connected in 1.36 seconds after fixture admission in the timed run.                                                                      |
| Layout, capture, and recording | Switched all four presets, started and stopped Chromium screen capture, and downloaded a 504,607-byte WebM. Guest recording notice, host mute, and live camera consent withdrawal were observed.                                                                                                                                                           |
| Audience transport             | Actual stage WHIP reached MediaMTX 1.21.4 with H.264 and Opus. Its HLS manifest advertised both tracks, and an independent browser decoded the WHEP video stream. Theater account/control responses were fixture-hosted.                                                                                                                                   |
| Visual sync                    | The same layout marker was 42 ms from its expected WebM position against a 750 ms tolerance, and appeared in the WHEP viewer 68 ms after the layout action against a 1,000 ms local viewer tolerance. The final run measured one visual marker and isolated it from the earlier screenshare transition after an earlier run misidentified that transition. |
| Recovery                       | Fixture signalling interruption recovered. Fixture revocation disconnected the affected guest while the other remained connected.                                                                                                                                                                                                                          |

The full acceptance gate still requires a single connected run through the deployed CMS and theater controls with guests on separate networks, real-device A/V sync and viewer delay measurements, and live revoke/reconnect through the production routes. The local evidence does not establish TURN behavior, HLS player delay, or LiveKit performance.
