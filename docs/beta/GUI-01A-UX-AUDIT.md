# BETA GUI-01A — Interface and user experience audit

Date: 2026-11-08. Scope: audit only; no implementation changes, migrations, configuration changes, account creation, authentication bypass, or content writes.

## 1. Executive findings and evidence boundaries

The application has substantial existing editorial and operational capability. Its main UX problem is how that capability is arranged: database-oriented forms, overlapping navigation, and large operational workspaces obscure common tasks. Consolidate the current Payload/React interface, retain Lexical for prose and Puck for presentation, and improve task hierarchy before considering another authoring application.

The five highest-impact problems are:

1. **Writing does not lead the content form.** The first tab contains tenant/ownership/type controls before the headline and body, followed by numerous classification fields. The grouping helper preserves schema order rather than following its own name lists. Source: `src/collections/Publishing.ts`, `publisherFieldGroups`, `Content`; routes `/admin/collections/content/create?contentType=article` and `?contentType=page`. Source-confirmed arrangement; actual above-the-fold body position **NOT VERIFIED**.
2. **Save, preview, publishing, scheduling and history are scattered.** Saved draft preview is inside SEO, publication is a status change plus Save, scheduling is a list-row action for approved records, and history is a separate view. Source: `PublishingCenter.tsx`, `DiscoveryPanel.tsx`, `DraftAutosave.tsx`, `ScheduleContentAction.tsx`, `RevisionHistory.tsx` under `src/modules/admin/`. Source-confirmed; end-to-end current interaction **NOT VERIFIED**.
3. **There is no consistent administration shell across entry points.** Flat injected links coexist with Payload collection groups; explicit frontend admin pages use the public frontend layout, while custom Payload views use Payload's layout. Several URLs have both registrations. Source: `src/payload.config.ts`, `src/modules/admin/PublishingLinks.tsx`, `src/app/(payload)/layout.tsx`, `src/app/(frontend)/layout.tsx`, `src/app/(frontend)/admin/layout.tsx`. Rendered shell and route precedence **NOT VERIFIED** for authenticated views.
4. **Tenant context is not communicated consistently.** The site switcher updates optimistically and does not check the POST response; MediaLibrary independently falls back to the first active site using an elevated query. NavigationCenter maintains another site selection flow. Source: `SiteSwitcher.tsx`, `MediaLibrary.tsx`, `NavigationCenter.tsx`. This is a UX/context risk, not evidence that protected writes bypass server policy.
5. **Operations dominate everyday work and styling varies by subsystem.** Media operations render before the media library; audience/workflow/release screens contain many sections and action types. Payload tokens, frontend theme classes, inline styles and hardcoded colors coexist. Source: `MediaLibrary.tsx`, `MediaCommandCenter.tsx`, `AudienceCommandCenter.tsx`, `EditorialWorkflowCenter.tsx`, `ReleaseCenter.tsx`, `SiteSwitcher.tsx`, `src/modules/presentation/themes/starter.css`. Source-confirmed structure; rendered density/contrast **NOT VERIFIED**.

## 4. Publishing-editor diagnosis

### Why the body is hard to find

`Content` in `src/collections/Publishing.ts` is the shared record for article and page plus six other content types. `publisherFieldGroups` buckets existing fields into tabs, pushing each field as it iterates the original array. Its `names` arrays classify fields; they **do not reorder** them. There is no dedicated article/page writing screen in the current entry path: PublishingCenter links directly to native Payload create/edit.

Writing order is: `site`, `publication`, `space`, `owner`, `contentType`, UI `contentTypeEntry`, `title`, `body`, UI `draftAutosave`, `summary`, `subtitle`, `excerpt`, `authors`, `sections`, `categories`, `collections`, `sortOrder`, `topics`, `tags`, `series`. Thus six entries, including five actual inputs and one UI component, precede the headline; body follows title. Claims that body is absent, is raw JSON, or must be below a particular viewport are unsupported. It is a Lexical `richText` field with default features, media/content relationships and an editorial callout block.

Content has 76 top-level entries: Writing 20, Presentation 12, Media 1, Publish 7, SEO 9, Advanced 27. These include five UI fields and one hidden field overall. Presentation contains two page-only conditional fields (`parentPage`, `pageTemplate`); Advanced includes hidden `publicModifiedAt`. Exact visible control counts also depend on arrays, conditions, access and editor initialization. Existing grouping already improves upon one unbroken form, but Writing remains overloaded.

### Draft, preview and publication interaction

- `ContentTypeEntry.tsx` waits for Payload form initialization, then reads article/page from the create query only when contentType is empty. Preserve this to avoid resetting an existing record or racing Payload initialization.
- `DraftAutosave.tsx` uses the native form submission/validation path. It requires an existing ID and status `draft` or `updated`, waits two seconds after changes, pauses during initialization/processing, and exposes save failure/retry. New unsaved content is **not already autosaved**. Moving the indicator must retain truthful first-save instructions and validation/lock errors.
- `DiscoveryPanel.tsx` requires a saved ID, loads resolved discovery state on lastUpdateTime, then creates a saved preview via POST `/api/admin/content/preview`. Opening preview is a second link action; the panel states 30-minute expiry. It does not promise preview of unsaved keystrokes. A future toolbar should save successfully first or explicitly label “saved preview.”
- Current list guidance says set status to published and save. `Content` guards, `src/modules/editorial/review-write-guard.ts` and companion persistence remain authoritative. The recommended Publish control is a presentation of existing permitted transitions, not a new shortcut around review or quality gates.
- Scheduling lives in `ScheduleContentAction.tsx` on approved list items for owner/administrator roles and uses `/api/admin/calendar/schedule` with revision sequence. Preserve timezone, approval, sequence and stale-state handling; an editor shortcut must reuse this path rather than setting a date/status field independently.
- `RevisionHistory.tsx` fetches `/api/admin/workflow/revisions`, restores by POST, and explicitly says restore creates a new saved revision while public body remains pinned until publication. Workflow comparison lives in `EditorialWorkflowCenter.tsx`; do not substitute Payload versions without proving equivalent contracts. Content does not configure native `versions` in the inspected definition.
- Citations exist in `ArticleFamilyContent` (`sourceReferences`, `citations`, `citationAttachments`, `bibliography`) and `src/modules/editorial/persistence.ts`; Sources is an optional module collection. No citation-specific Lexical authoring control was found in Content's configured feature list or the ordinary Writing tab. Preserve the supported service/companion workflow; do not promise a bibliography toolbar or add one as a styling task.
- `AiProposalActionField` supplies proposal entry points; keep accept/reject governance and original-target identity separate from direct manual edits.

### Architecture decision

**Recommend a customized Payload content edit experience first.** Use supported field layout/UI/component slots around the current native form, retaining its validation, access, locks and state. Reuse `ContentTypeEntry`, `DraftAutosave`, `DiscoveryPanel`, scheduling and revision components. Begin with layout and action placement; verify installed Payload extension contracts before choosing a full edit-view override.

A standalone authoring application would duplicate form state, dirty-navigation handling, tenant context, relationship pickers, validation, lock conflicts, autosave and error recovery. There is insufficient current visual evidence to justify that cost. If supported native customization later proves inadequate, assess a dedicated view inside the same Payload shell against those exact contracts; do not build another backend/editor or replace Lexical with Puck. Puck remains the existing page-layout/presentation canvas, not the article body editor.
