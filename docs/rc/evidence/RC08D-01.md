## 1. Issue & Failing Reproduction

### Reported Blocker
1. An administrator or owner navigates to Site Settings (`/admin/globals/site-settings`).
2. Site Settings saves successfully (`POST /api/globals/site-settings`).
3. Reloading the native Payload editor (`GET /admin/globals/site-settings`) produced a blank page (`DocumentView` returning `undefined`).
4. Server threw:
   ```text
   TypeError: Cannot read properties of undefined (reading 'id')
       at getIsLocked (@payloadcms/next/dist/views/Document/getIsLocked.js)
   ```
5. Locking must remain enabled across the platform; locking cannot be disabled or bypassed to pass.

### Transient Reproduction & Trace
- When `payload-locked-documents` stores a lock for `site-settings`, `getIsLocked.js` queries `payload-locked-documents` for active locks.
- Under Payload's Drizzle adapter with PostgreSQL, relationship fields (`user`) can project in polymorphic shapes:
  - Polymorphic populated: `{ relationTo: 'users', value: { id: '...', email: '...' } }`
  - Polymorphic unpopulated: `{ relationTo: 'users', value: 'userId' }`
  - Monomorphic object: `{ id: '...', email: '...' }`
  - Unpopulated string ID: `'userId'`
  - Undefined/null (e.g. concurrent cleanup or missing reference)
- Upstream `getIsLocked.js` accessed `docs[0].user?.value`. When `currentEditor` was unpopulated or undefined, `extractID(currentEditor)` called `.id` on undefined, throwing an unhandled exception that broke the React server component render, leaving a blank editor page.
- Furthermore, if `currentEditor` was populated polymorphically, prior naive patches treated `currentEditor.id ?? currentEditor.value` as the ID, yielding `{ id: '...' }` (object) which coerced to `"[object Object]"`, failing identity comparison with `req.user.id` and falsely declaring the owner locked out of their own editor!

---

## 2. Root Cause Analysis

1. **Polymorphic Lock Relationship Representation**:
   Payload `payload-locked-documents` configures:
   ```js
   {
     name: 'user',
     type: 'relationship',
     relationTo: authCollections,
     required: true
   }
   ```
   In PostgreSQL Drizzle queries, relationship depth resolution is non-uniform between collection operations and direct global lookups.
2. **Missing Normalization Boundary**:
   Upstream `@payloadcms/next/dist/views/Document/getIsLocked.js` did not safely normalize polymorphic relationship shapes, unpopulated ID values, or missing user relations.
3. **Fragile Exception Boundary**:
   Any exception during lock checking aborted the entire Next.js Server Component render instead of gracefully failing open (unlocked) with diagnostic logging.

## 3. Repair Implementation

### Files Modified:
- `scripts/apply-patches.mjs`:
  - Implements the idempotent patch applied to `node_modules/@payloadcms/next/dist/views/Document/getIsLocked.js`.
  - Normalizes owner user across polymorphic populated, polymorphic unpopulated, monomorphic, and raw ID shapes.
  - Implements fallback user hydration via `req.payload.findByID` with `overrideAccess: true` if the relation was not populated.
  - Adds fail-safe defaulting: if a lock document is corrupt or missing an owner, returns `{ isLocked: false, currentEditor: null }`.
  - Wraps the entire operation in a top-level try/catch that logs to `req.payload.logger` and returns `{ isLocked: false }`.
- `package.json`:
  - Registered `"postinstall": "node scripts/apply-patches.mjs"` to ensure the patch is automatically applied on every install.
- `scripts/build.mjs`:
  - Imports `./apply-patches.mjs` prior to triggering Next.js build compilation.
- `tests/unit/rc08d-lock-projection.test.ts`:
  - 9 unit tests verifying all lock-owner projection shapes, self-editing, concurrent editor lockouts, corrupt locks, and fallback handling.
- `tests/integration/rc08d-lock-projection.integration.test.ts`:
  - 8 end-to-end integration tests on isolated PostgreSQL acceptance database executing the full user journey.
