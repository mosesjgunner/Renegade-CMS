## Continuation — Stage 4 (Nov 19, 2026): visibility policy, marked examples, impact preview, next steps

### Site visibility / coming-soon policy

- Storage: additive `visibility` select on the Payload-managed `sites` collection (`src/collections/Sites.ts`): `public | coming-soon | private`, default `public`. Because `sites` is SQL-backed, it ships with a Payload migration (`src/migrations/20261119_130000_uxi06_site_visibility.ts`, registered in `src/migrations/index.ts`): one `ADD COLUMN IF NOT EXISTS ... DEFAULT 'public' NOT NULL`, so every existing site keeps today's behavior (public) until an operator explicitly changes it. `src/payload-types.ts` was updated to match (field optional-with-default so existing site-create call sites are untouched).
- Enforcement point: the server render boundary, not `noindex`. `src/modules/public/site-visibility.ts` exposes `resolvePublicSiteAccess(payload, { siteId, headers })`; both public page routes call it before any content query — `src/app/(frontend)/page.tsx` (home) and `src/app/(frontend)/[...path]/page.tsx` (every canonical path, plus both `generateMetadata` implementations, which return only the site name + noindex for gated anonymous visitors). Anonymous visitors to a coming-soon/private site get `src/modules/public/ComingSoonPage.tsx` (site name + plain note; private adds a sign-in link) and no site content is loaded for them at all. Signed-in users pass only with an operator grant covering the site (global owner qualifies) — that is the preview path.
- Setup/launch wiring: `OnboardingInput.siteVisibility` (validated in `operations/onboarding.ts`; applied on site creation and whenever setup supplies it; a rerun without it never changes the policy) is offered in the setup form's step 4 as "Who can see your site?" — Make site public / Coming soon / Keep working privately — and shown in the step-5 review. The setup-draft sanitizer allowlists it. Guided setup shows the current state and offers the same three choices (via the starters API `set-visibility` action). Default for a freshly set-up site remains public, as before.

### Marked example content + safe remove/replace

- Provenance marker (no new schema; fields the collections already carry): full starters stamp `content.importSourceSystem = starter:<id>` (pre-existing) plus a new `importSourceChecksum` — a SHA-256 over the installed title/summary/status/body (`src/modules/starters/provenance.ts`), written in `starters/service.ts` for pages and articles. Onboarding starter content (`importSourceSystem = onboarding-starter`) gets the same checksum in `operations/onboarding.ts`, whose pristine check now prefers the checksum while keeping the original field comparison for legacy records. Starter layouts keep their existing baseline in `revisionHistory` (`starter-install`/`starter-upgrade` actions; onboarding home layout: `source: onboarding-starter`).
- Edited-content rule (stated + tested): an item is a removable example only while it still hashes to its install checksum (content) or its blocks still match its starter baseline (layouts). Any operator edit makes it protected — removal reports it and never touches it. Legacy content without a checksum falls back to an exact comparison against the starter definition; legacy onboarding layouts without a block baseline are protected (an edit cannot be ruled out). Operator-created content carries no provenance and is never listed.
- Remove-examples: `src/modules/starters/examples.ts` (`listStarterExamples` / `removeStarterExamples`), exposed via the starters API actions `examples` (preview: exact count + titles, split removable vs. protected-edited, before anything happens) and `remove-examples` (classification recomputed at removal time). Guided setup renders the preview list and requires an explicit confirm step. Removal deletes where the platform allows it; content carrying editorial revision history cannot be deleted (the hierarchy guard), so those examples are unpublished to draft instead — each result item records `deleted` vs `unpublished`. Scope note: media assets and products installed by a starter are not removed (they may be referenced by kept content); removal covers content + layouts, which is the visitor-visible example surface.

### Starter-change impact preview

Guided setup's full-starter action first calls the starters API `plan` action (`planStarterInstall`): on a populated site it shows, in plain language, how many pages/posts, design sections, and images would be added and which existing items overlap (existing content is preserved — install still refuses silent overwrite), and requires an explicit confirmation checkbox before installing. On an empty site it installs directly.
